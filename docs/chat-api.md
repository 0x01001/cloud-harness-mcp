# Independent Chat API

`apps/chat-api` is an independent inference-only Node.js process, not `/mcp`, the dashboard-managed MCP key gateway, or the internal `apps/model-gateway` leased/budgeted agent service. MCP, runner, database, Docker/Colima, and Cloudflare do not need to run. No MCP routes, tools, schemas, or plugin behavior change. Tool definitions/calls/results in chat payloads are data; this app executes no tools or host/workspace operations.

The complete user setup, config template, defaults, SDK usage, smoke instructions, and macOS lifecycle are in the [Chat API guide](https://docs.harness.agentkit.best/chat-api) ([source](../docs-site/chat-api.md)). This internal page records boundaries without duplicating the mutable command/config inventory.

## Executable authorities

- [`apps/chat-api/src/config.ts`](../apps/chat-api/src/config.ts): accepted environment names, defaults/ranges, private config parsing, permissions/key-value distinctness, model allowlist.
- [`apps/chat-api/.env.example`](../apps/chat-api/.env.example): chat-only template; copy to ignored `apps/chat-api/.env` for the default `npm run start:chat` path, derived from source/compiled module location, not CWD. `CHAT_CONFIG_FILE` retains an absolute external private config override. The root `.env.example` remains for MCP.
- [`apps/chat-api/src/index.ts`](../apps/chat-api/src/index.ts) and [`app.ts`](../apps/chat-api/src/app.ts): loopback binding, fixed routes, Host policy, constant-time Bearer auth, envelope/error/admission/deadline rules, shutdown.
- [`proxy.ts`](../apps/chat-api/src/proxy.ts) and [`egress.ts`](../apps/chat-api/src/egress.ts): fixed public HTTPS destinations, DNS validation/socket pinning, redirect rejection, rebuilt provider headers.
- [`package.json`](../package.json): Node >=24 and npm command authority; [`Makefile`](../Makefile) wraps setup/key-generation/lifecycle commands. `make setup` / `npm run chat:setup` bootstraps pinned Node 24.21.0 and npm 11.21.0 in ignored `.local-runtime/` using existing Node/npm, runs `npm ci` and `build:chat`, and checks ngrok's version/required CLI flags. If ngrok is absent on macOS, it uses existing Homebrew with `brew install ngrok`; Homebrew is never installed automatically. `make gen` / `npm run chat:gen` builds chat and creates a key without controlling services.
- [`scripts/chat-runtime.mjs`](../scripts/chat-runtime.mjs): macOS private config paths, owned-process/readiness checks, two scoped LaunchAgents, ngrok arguments, restart bounds and bounded sanitized logs with live following.
- [`scripts/smoke-chat.mjs`](../scripts/smoke-chat.mjs): pinned official OpenAI SDK 7.27.0, `maxRetries: 0`, discovery/auth and both APIs' JSON/SSE checks.

After setup, `make` prepends `.local-runtime/node_modules/.bin` for all child commands, including npm lifecycle scripts. Direct `node`/`npm` still use the global runtime unless invoked with `PATH="$PWD/.local-runtime/node_modules/.bin:$PATH"` from the repository root. Setup changes neither global Node/npm nor shell profiles (an existing global Node 22 remains Node 22). It does not read/write private config or credentials, generate keys, install/start/stop services, open a tunnel, or call the provider. Credentials, ngrok authtoken, and assigned domain remain manual prerequisites; **setup is not install**.

## Operating boundary

The only inference surfaces are authenticated `GET /v1/models`, `POST /v1/chat/completions`, and `POST /v1/responses`. `/healthz` and `/readyz` are anonymous minimal **local** status, not a provider/credential/quota probe. The listener is loopback-only; ngrok forwards only its chat port. Wrong/missing chat keys fail even on localhost; Access/forwarding headers cannot authenticate. There is no browser/CORS surface or Responses CRUD/WebSocket API.

Choose one public HTTPS upstream with native Chat Completions, native Responses, and `/models`; at least one exact allowed model must work with both APIs. The app does not translate, fall back to another provider/model, remap models, or certify provider feature parity. Body/envelope/content-type validation and byte/deadline limits bound pass-through; successful JSON and native SSE preserve supported upstream fields/events. Interrupted streams do not receive fabricated terminal success. Discovery is filtered, not a substitute for live inference acceptance.

`CHAT_UPSTREAM_API_KEY` accepts one provider key or an ordered comma-separated list of nonempty unique keys, with no spaces. Each key retains the same validation: 32–4096 ASCII characters, no whitespace/control characters or placeholders. Every request starts with the first key and attempts each key at most once. All three upstream routes can advance to the next key only before the downstream response starts, on HTTP `429` with a valid native JSON error whose `code` is `insufficient_quota`, or whose `type` is `insufficient_quota` when `code` is absent/null. A different code takes precedence over type. Attempts keep the same endpoint, model, body, HTTPS policy, admission slot, and total request deadline; the prior response body is disposed before advancing. There is no sticky/global rotation or generic retry for rate limits, `401`, `5xx`, network/timeouts, or SSE failures, and no replay after SSE headers/content. Exhaustion returns the last sanitized `429` error. Keys in the same provider project may share quota, so more keys do not necessarily add capacity.

Every primary/generated client key, including newly generated keys, must differ from every provider key. Sanitized upstream errors redact all configured client/provider keys, including untried provider keys. Keep credentials out of logs and public examples.

The exact repository `apps/chat-api/.env` is the only checkout exception: an owner-owned regular file at exact `0600`, with an owner-owned immediate parent that is not group/world writable (`0755` allowed). Every other private config/key file, including an explicit config override, must resolve outside the checkout at exact `0600` with an owner-owned parent at exact `0700`. Leaf/immediate-parent symlinks are rejected; ancestor symlinks are not universally prohibited. `CHAT_UPSTREAM_API_KEY` holds the provider credential inline in the config; the removed `CHAT_UPSTREAM_API_KEY_FILE` setting has no compatibility alias. Prepare the required `.env` with an absolute `CHAT_API_KEY_FILE`, then use `make gen` / `npm run chat:gen`: the first run exclusively creates the missing primary file; subsequent runs preserve it and exclusively add `${CHAT_API_KEY_FILE}.d/<random-UUID>.key`. Keys use `crypto.randomBytes(32).toString('hex')`; files are `0600`, directories `0700`, and the newly generated key is printed for copying while its file is persisted internally for server authentication. Remote `Authorization: Bearer <chat-key>` uses the key text, never the provider key or file path. At startup the server accepts the primary plus generated keys, all with the same full inference access and shared admission/provider quota, not per-user budgets or admin rights. Missing, unknown, placeholder, reused, unsafe config or invalid generated-key entries fail closed. Never commit secrets; keep chat, provider, ngrok, and MCP credentials separate. Admission limits are in memory and reset on restart; provider budgets/quotas/alerts are still required.

`make gen` or `npm --silent run chat:gen` prints only the freshly generated 64-hex key followed by a newline; build diagnostics go to stderr. Copy the printed key directly into `Authorization: Bearer <chat-key>`, never a file path. The key file is persisted internally for server authentication; existing client keys and the provider key are not printed. Terminal output is now sensitive: avoid CI/shared logs and distribute the key securely. Plain `npm run chat:gen` also prints npm script banners.

## Data and lifecycle

No conversations/responses are stored locally, and app/launcher logs must not contain prompts, completions, bodies, or secrets. Responses `store`/`previous_response_id` semantics and retention remain upstream-owned; `store: false` is not proof of zero retention. A `previous_response_id` may depend on the originating provider project and is not portable across projects; quota failover to a key in another project may therefore reject a continuation. No local response retrieve/delete/cancel endpoints exist. Ngrok and the provider are independent data trust boundaries: review upstream retention and ngrok account capture settings even though tunnel inspection is disabled.

`make log` (also `make logs`) follows scoped lifecycle and request/response metadata in real time; `LOG_ARGS=--no-follow` prints recent records and exits. The app emits a generated correlation ID on arrival and one completion/abort record with HTTP status and elapsed time. Successful `GET /healthz` and `GET /readyz` probes emit neither record; failed or aborted probes emit both records on completion. Readiness monitoring remains enabled. Fixed route/method labels keep arbitrary URLs, headers, model IDs, bodies and secrets out of logs. The supervisor accepts only validated metadata over IPC, never raw child output, and serializes private rotating writes with a bounded queue; disk failures or queue saturation can lose log events without changing inference behavior. These are operational diagnostics, not a durable audit ledger. Rebuild chat and restart the installed runtime to enable events from an older running process; viewing logs does not restart services.

Follow the guide's foreground build/start and **authorized** local SDK smoke before tunnel rollout; repeat the smoke from another machine through ngrok. Generation does not install/start/stop/restart services or make provider requests. Keys/config are loaded only at startup: after adding, removing, or changing any client/provider key, restart the foreground process or use `make stop` then `make start` for the already-installed runtime, retaining its config-path override; `make start` alone does not restart a running app. To revoke one generated key, remove only its specific `.d/<UUID>.key` file and restart; leave the primary and other generated files unchanged. Primary rotation replaces only the primary private file while stopped; generated keys remain valid unless separately removed. Check revoked-key rejection and retained/new-key acceptance after an operator-authorized restart. Revoke provider/ngrok credentials at their owners separately. Stop/uninstall only affects this chat instance and retains private config/keys/logs; it does not touch MCP state/deployments.

LaunchAgents work after user login, not guaranteed before login or after logout. Sleep/logout/network changes can interrupt streams; reconnection/restart does not replay inference. Runtime ownership/status is not public connectivity or model proof. Config path determines installed runtime identity: when migrating from the former external `chat.env` default, stop/uninstall the old registration with that explicit `CHAT_CONFIG_FILE` first, then install the intended app-local default or keep the explicit external override consistently. Reinstall registration after changing config/checkout/executable paths; changing defaults does not migrate old jobs automatically.

`make install` after setup records an absolute project-local Node executable in the LaunchAgents. Do not remove `.local-runtime/` while those jobs are installed; reinstall registration if the checkout moves or the selected executable changes.

Chat's ngrok lifecycle requires a literal absolute `CHAT_NGROK_CONFIG_FILE` in the selected private Chat `.env`, for example `/absolute/private/ngrok-translate.yml`. It reads only that file's setting, not an ambient shell override, and always passes explicit `--config`; there is no default/shared-config fallback. The same executable is fine, but this file and its authtoken must be independent of other applications; never copy their secrets or run bare `ngrok config add-authtoken`. An already configured dedicated token stays untouched: no token-add command is needed. For a new config, use a private editor with ngrok v3 `agent.authtoken` and `agent.web_addr: false` (avoids another agent's local port 4040), exact owner-owned file `0600`/directory `0700`, and no leaf/immediate-parent symlink. The [user guide](../docs-site/chat-api.md#dedicated-ngrok-configuration) includes the template and explicitly scoped CLI alternative with its argv/history security caution. Use a different assigned domain; separate configs/tokens do not bypass ngrok account or concurrent-agent limits.

Install/start retain instance-scoped LaunchAgent labels/state and never modify another application's config or agent. Install pins the selected ngrok config path; changing `CHAT_NGROK_CONFIG_FILE` or using a prior shared-config manifest requires reinstall before start. Stop/uninstall remain available only for its verified old jobs: retain the exact `CHAT_CONFIG_FILE` identity when cleaning them up, select and secure the dedicated ngrok config, then install that intended instance. No credentials are created or migrated automatically.
